# WB + OZON Stock Bot

Бот для остатков и FBS-заказов Wildberries и OZON:

- автоматически получает карточки товаров и `chrtID`;
- автоматически определяет единственный активный склад продавца;
- проверяет остатки FBS через Marketplace API;
- проверяет суммарные остатки по всем складам WB через Analytics API;
- отправляет уведомление об окончании только когда суммарно `FBS = 0` и `WB = 0`;
- в этом уведомлении предлагает кнопки `1`, `5`, `Не добавлять` для управления FBS;
- отдельно уведомляет, когда на WB было `0`, стало `> 0`, а на вашем FBS-складе товар всё ещё есть;
- в этом уведомлении предлагает `Обнулить FBS` или `Не обнулять FBS`;
- хранит предыдущие значения в SQLite;
- умеет отвечать в Telegram на `/stocks`, `/stock`, `/zero`, `/status`, `/id`;
- показывает `/stocks` выровненной моноширинной таблицей с кнопками переключения страниц;
- сохраняет недоставленные stock-уведомления в SQLite и повторяет их после восстановления Telegram/интернета;
- обнаруживает длительные разрывы мониторинга и после восстановления сверяет заказы и остатки;
- восстанавливает пропущенные FBS-заказы за период через историю заказов WB и проверяет их текущие статусы;
- при настроенном OZON Seller API загружает каталог и FBS-остатки OZON;
- уведомляет о новых FBS-отправлениях OZON и позволяет перевести их в сборку кнопкой «Собрать» без создания поставки и грузоместа;
- объединяет товары WB и OZON по артикулу продавца в web CRM;
- запускает небольшую web CRM для учёта остатков.

## 1. Токены

### Wildberries

Используется один `WB_TOKEN` с уровнем **Чтение и запись** и категориями:

- **Контент** — список карточек и `chrtID`;
- **Маркетплейс** — чтение склада FBS и изменение его остатков;
- **Аналитика** — остатки FBW.

Один и тот же `WB_TOKEN` используется и для чтения, и для записи остатков FBS. Токен хранится только в `.env` и не вставляется в исходный код.

### OZON

Интеграция OZON необязательна. Для неё нужны `OZON_CLIENT_ID` и `OZON_API_KEY` из кабинета продавца. Если обе переменные пустые, OZON-часть не запускается и существующий WB-функционал работает как раньше.

```env
OZON_CLIENT_ID=
OZON_API_KEY=
# Если активный FBS/rFBS-FBO один, бот выберет его автоматически.
# Архивные/заблокированные склады при авто-выборе не учитываются.
# Если активных FBS/rFBS-складов несколько — укажите нужный warehouse_id.
OZON_WAREHOUSE_ID=
OZON_ORDER_CHECK_INTERVAL=30
OZON_STOCK_CHECK_INTERVAL=300
```

Артикул продавца OZON (`offer_id`) считается тем же каноническим SKU, что и артикул продавца WB. Товар может присутствовать только на WB, только на OZON или одновременно на обоих маркетплейсах.

Для FBS-заказов OZON бот получает отправления в статусе `awaiting_packaging`. В Telegram для такого отправления доступны кнопки:

- **Собрать** — перед действием бот повторно читает отправление и, если оно всё ещё ожидает сборки, переводит его в следующий этап через OZON Seller API;
- **Не собирать** — запоминает решение и больше не предлагает это отправление через `/status`.

В отличие от WB, в этом сценарии OZON не требует от бота выбирать/создавать поставку или создавать грузоместо: действие выполняется непосредственно для FBS-отправления.

### Telegram

1. Создайте бота через `@BotFather`.
2. Скопируйте токен бота в `.env`.
3. На первом запуске можно оставить `TELEGRAM_CHAT_IDS=` пустым.
4. Напишите боту `/id`.
5. Бот вернёт ваш `chat_id`; вставьте его в `.env` и перезапустите сервис.

### Значки WB и Ozon в Telegram

В уведомлениях используются бренд-маркеры: **🟣 WB** и **🔵 Ozon**. При желании их можно заменить настоящими Telegram custom emoji с логотипами маркетплейсов:

```env
TELEGRAM_WB_EMOJI_ID=
TELEGRAM_OZON_EMOJI_ID=
```

Публичные Telegram-наборы с подходящими логотипами существуют, например `MarketplaceEmoji` (WB/Ozon) и `WB_light` (Wildberries). В переменные нужно указать именно `custom_emoji_id` выбранных значков, а не имя набора. Если ID не заданы или Telegram отклонит custom emoji, бот автоматически использует Unicode fallback и продолжит отправку уведомления.

По текущему Bot API custom emoji в сообщениях бота доступны, в частности, когда владелец бота имеет Telegram Premium; поэтому fallback оставлен обязательным.

## 2. Локальный запуск / запуск на VM

Требуется Python 3.11+.

```bash
cd wb_stock_bot
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
nano .env
python -m app.main
```

На самом первом запуске текущие остатки считаются базовым состоянием и не генерируют шквал уведомлений. После этого бот уведомляет об окончании товара только при переходе общего доступного остатка в ноль: одновременно `FBS = 0` и `WB = 0`. Ноль только в одном канале уведомлением об окончании не считается. Дополнительно для складов WB он уведомляет один раз при переходе `0 -> >0`, но только если в этот момент на вашем FBS-складе этого товара больше `0`. После обычного перезапуска сервис сравнивает свежие данные с сохранённым состоянием SQLite, поэтому может поймать изменение, случившееся во время простоя.

## 3. Telegram-команды

- `/stocks_wb` — обновить и показать остатки WB FBS + суммарные остатки FBW;
- `/stocks_wb 2` — открыть страницу 2 WB напрямую;
- `/stocks_ozon` — обновить и показать остатки Ozon FBS + FBO;
- `/stocks_ozon 2` — открыть страницу 2 OZON напрямую;
- `/stocks_main` — показать полный физический остаток **«Моего склада»**;
- `/stocks_main 2` — открыть страницу 2 «Моего склада»;
- `/stock SKU-001` — найти товар в WB по артикулу продавца;
- `/set SKU-001 7` — установить лимит **«Доступно для заказа»** в 7 шт.; «Мой склад» при этом не меняется;
- `/set_main SKU-001 +5` — добавить 5 шт. к полному физическому остатку;
- `/set_main SKU-001 -2` — убрать 2 шт. из полного физического остатка;
- `/zero` — показать товары WB, у которых `0` на FBS и/или FBW;
- `/fbs_zero_all` — после подтверждения массово установить «Доступно для заказа» в 0 и синхронизировать FBS;
- `/fbs_restore` — восстановить сохранённые значения «Доступно для заказа» после массового нуля;
- `/ozon_fbs_zero_all` — альтернативная команда того же массового обнуления общего доступного лимита;
- `/ozon_fbs_restore` — восстановить сохранённые значения общего доступного лимита;
- `/status` — вручную сверить новые WB/OZON-заказы и нерешённые ситуации по остаткам обеих площадок;
- `/id` — показать Telegram `chat_id`.

`/stocks_wb` выводится моноширинной таблицей без цифрового артикула WB:

```text
   Артикул                         WB FBS  FBW
🟣 SKU-001                               7   42
🟢 SKU-002                               0   11
```

Под сообщением отображаются inline-кнопки `◀️  1/3  ▶️`. Нажатие кнопок редактирует текущее сообщение и не делает новый запрос к WB. Маркеры в `/stocks_wb`: 🟣 — товар есть одновременно на FBS и на FBW; 🟢 — товар есть только в одном из двух каналов; 🔴 — товара нет ни на FBS, ни на FBW.

`/stocks_ozon` использует ту же пагинацию, но показывает колонки `FBS` и `FBO`. Маркеры аналогичны: 🟣 — товар есть одновременно в Ozon FBS и FBO; 🟢 — только в одном из каналов; 🔴 — отсутствует и в FBS, и в FBO.

`/stocks_main` показывает артикулы и полный физический остаток «Моего склада». Команда использует ту же постраничную навигацию через inline-кнопки. 🟢 означает положительный физический остаток, 🔴 — нулевой.

`/set_main` принимает только **дельту со знаком**. `+N` увеличивает физический остаток, `-N` уменьшает. Команда не меняет «Доступно для заказа», пока физический остаток остаётся не меньше текущего доступного лимита. Если после уменьшения «Мой склад» становится меньше «Доступно», бот автоматически уменьшает «Доступно» до нового физического остатка и синхронизирует активные FBS.

## 4. «Мой склад» и «Доступно для заказа»

Для каждого артикула бот хранит два связанных значения:

- **Мой склад** — полный физический остаток товара у продавца;
- **Доступно для заказа** — сколько единиц из этого полного остатка разрешено продавать через FBS прямо сейчас.

«Доступно для заказа» не является отдельным складом и не вычитается из «Моего склада». Например, если физически есть 20 шт., а продавать сейчас нужно только 6, значения будут: **Мой склад = 20**, **Доступно = 6**.

Изменение «Доступно для заказа» через CRM или `/set` меняет только продаваемый лимит. «Мой склад» остаётся прежним. При этом «Доступно» не может быть больше полного физического остатка.

Если вручную уменьшить «Мой склад» ниже текущего «Доступно», бот автоматически уменьшит «Доступно» до нового физического остатка и синхронизирует FBS. Увеличение «Моего склада» само по себе «Доступно» не увеличивает.

После каждого изменения «Доступно» бот публикует это число в WB FBS и Ozon FBS, кроме площадки, которая временно подавлена из-за наличия товара на её собственном складе. Фоновая сверка раз в 30 секунд держит обычный FBS равным «Доступно», а подавленный FBS — равным 0.

### Продажи

Новый FBS-заказ уменьшает **оба** значения на проданное количество:

- «Мой склад» уменьшается, потому что физически товар ушёл;
- «Доступно для заказа» уменьшается на то же количество;
- новое «Доступно» синхронизируется в активные WB FBS / Ozon FBS;
- один и тот же заказ/отправление не списывается повторно: обработанные события фиксируются в SQLite;
- остатки никогда не уходят ниже нуля.

Пример: **Мой склад = 20**, **Доступно = 6**. После продажи 1 шт. станет **19** и **5**.

### Миграция со старой split-модели

Версии с PR #27-29 хранили «Мой склад» как остаток вне продаваемого пула, поэтому полный физический остаток приходилось считать как сумму двух колонок.

При первом запуске новой версии выполняется одноразовая миграция:

- текущее «Доступно» добавляется к старому значению «Моего склада»;
- само значение «Доступно» сохраняется;
- после этого «Мой склад» уже показывает полный физический остаток;
- миграция отмечается в SQLite и не повторяется при следующих перезапусках.

Сценарии индивидуального WB/OZON-подавления и массового нуля учитываются отдельно, чтобы физический остаток не задвоился.

### Обнуление при появлении товара на складе площадки

Индивидуальные WB/OZON-сценарии работают **по площадкам**:

- если товар появился на FBW, бот предлагает обнулить только **WB FBS**;
- если товар появился в FBO, бот предлагает обнулить только **Ozon FBS**;
- «Доступно для заказа» и «Мой склад» при этом не меняются;
- FBS второй площадки продолжает получать текущее значение «Доступно для заказа».

Когда остаток на собственном складе площадки снова становится нулевым, бот предлагает восстановить **только её FBS** до текущего значения «Доступно для заказа».

Ручное изменение `/set` или колонки «Доступно для заказа» не снимает такое платформенное подавление: активная площадка получает новое значение, подавленная остаётся на FBS=0 до окончания своего WB/FBO-сценария.

### Массовое обнуление и восстановление

Массовые команды `/fbs_zero_all` / `/fbs_restore` и `/ozon_fbs_zero_all` / `/ozon_fbs_restore` меняют только **«Доступно для заказа»**:

- при обнулении «Доступно» становится 0, а «Мой склад» не меняется;
- прежнее значение «Доступно» сохраняется;
- при восстановлении лимит возвращается, но не выше текущего физического остатка;
- WB FBS / Ozon FBS синхронизируются с восстановленным лимитом.

### Уведомления об окончании

Кнопки `1` и `5` в уведомлениях об окончании товара устанавливают «Доступно для заказа» в 1 или 5 шт. Они не изменяют «Мой склад». Если физический остаток меньше выбранного значения, бот не даст установить такой лимит.

## 5. Web CRM

CRM запускается в том же процессе и использует ту же SQLite-базу, что и Telegram-бот.

CRM сфокусирована только на остатках. В одной таблице показываются:

- **Мой склад** — полный физический остаток;
- **Доступно для заказа** — редактируемый лимит продаж через FBS;
- WB FBS, если товар существует на WB;
- остатки FBW, если товар существует на WB;
- Ozon FBS, если товар существует на OZON;
- остаток на складе OZON (FBO), если товар существует на OZON.

Таблица строится как объединение каталогов WB и OZON по артикулу продавца. Если товара нет на одном из маркетплейсов, соответствующая колонка показывает `—`, а не ложный ноль. Для общего артикула используется одна строка с отдельными значениями «Мой склад» и «Доступно для заказа».

Мониторинг и управление заказами WB/OZON из web CRM отсутствуют. Заказы обрабатываются через Telegram-бота.

В первой колонке сначала показывается **название товара**, ниже — артикул продавца. Колонки «Мой склад» и «Доступно для заказа» имеют отдельные числовые поля и кнопки ✓. Заголовок таблицы закреплён и остаётся видимым при прокрутке списка товаров.

Редактирование «Моего склада» меняет полный физический остаток. Редактирование «Доступно для заказа» меняет только лимит продаж и не изменяет физический остаток. Если новый физический остаток становится меньше текущего лимита, лимит автоматически уменьшается до физического остатка. После сохранения «Доступно» бот публикует это значение в активные WB FBS / Ozon FBS. Если marketplace API отклоняет запись, CRM показывает ошибку; сохранённый лимит остаётся в SQLite, и фоновая сверка повторит публикацию.

Для текущей локальной сети CRM можно слушать на всех интерфейсах, но разрешать доступ только из конкретных CIDR:

```env
CRM_ENABLED=1
CRM_HOST=0.0.0.0
CRM_PORT=8080
CRM_ALLOWED_NETWORKS=127.0.0.1/32,::1/128,192.168.1.0/24
CRM_USER=
CRM_PASSWORD=
```

В этом режиме устройство с адресом, например, `192.168.1.25` сможет открыть CRM по адресу сервера:

```text
http://<LAN-IP-сервера>:8080
```

а клиент из другой подсети получит HTTP `403`. CIDR-фильтр использует фактический IP TCP-клиента и не доверяет `X-Forwarded-For`.

`CRM_USER` и `CRM_PASSWORD` можно задать дополнительно — тогда Basic Auth будет требоваться даже внутри разрешённой сети. Если `CRM_HOST` нелокальный, но `CRM_ALLOWED_NETWORKS` пуст, логин и пароль обязательны.

Для доступа извне домашней/офисной сети по-прежнему рекомендуется не публиковать порт `8080` напрямую, а использовать VPN либо Nginx/Caddy с HTTPS.

## 6. Установка как systemd-service

Пример ниже рассчитан на Ubuntu/Debian и путь `/opt/wb-stock-bot`.

```bash
sudo useradd --system --home /opt/wb-stock-bot --shell /usr/sbin/nologin wb-bot
sudo mkdir -p /opt/wb-stock-bot
sudo cp -a . /opt/wb-stock-bot/
sudo chown -R wb-bot:wb-bot /opt/wb-stock-bot

sudo -u wb-bot python3 -m venv /opt/wb-stock-bot/.venv
cd /opt/wb-stock-bot
sudo -u wb-bot /opt/wb-stock-bot/.venv/bin/python -m pip install -r /opt/wb-stock-bot/requirements.txt

sudo cp /opt/wb-stock-bot/wb-stock-bot.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now wb-stock-bot
sudo systemctl status wb-stock-bot
```

Логи:

```bash
journalctl -u wb-stock-bot -f
```

После изменения `.env`:

```bash
sudo systemctl restart wb-stock-bot
```

## 7. Обновление сервера через GitHub

После того как рабочий каталог `/opt/wb-stock-bot` привязан к этому репозиторию, обычное обновление выглядит так:

```bash
cd /opt/wb-stock-bot
sudo -u wb-bot git pull --ff-only
sudo -u wb-bot /opt/wb-stock-bot/.venv/bin/python -m unittest discover -s tests -v
sudo systemctl restart wb-stock-bot
sudo systemctl status wb-stock-bot
```

Файлы `.env`, `data/`, SQLite-база и `.venv/` исключены через `.gitignore` и остаются локальными на сервере. Поэтому `git pull` обновляет исходный код, не затрагивая токены и сохранённое состояние остатков.

Если изменился `requirements.txt`, перед перезапуском дополнительно выполните:

```bash
sudo -u wb-bot /opt/wb-stock-bot/.venv/bin/python -m pip install -r /opt/wb-stock-bot/requirements.txt
```

## 8. Как считаются остатки

### Один склад продавца (FBS)

Бот получает единственный активный склад через `GET /api/v3/warehouses`, затем запрашивает остатки по `chrtID` через `POST /api/v3/stocks/{warehouseId}`. Если активных складов окажется не один, бот намеренно остановится с ошибкой, чтобы случайно не мониторить не тот склад.

### FBW

Бот получает строки остатков через `POST /api/analytics/v1/stocks-report/wb-warehouses` и суммирует `quantity` одного `nmID` по всем размерам и складам WB.

Wildberries обновляет данные этого аналитического метода примерно раз в 30 минут. Поэтому фоновая проверка WB по умолчанию тоже выполняется раз в 30 минут. Команда `/stocks_wb` делает свежий запрос, если это не нарушает лимит API.

### Ozon FBS и FBO

При настроенном OZON Seller API бот получает FBS/FBO-разбивку через `POST /v4/product/info/stocks`. FBS обновляется через `POST /v2/products/stocks` на выбранном складе продавца. Если `OZON_WAREHOUSE_ID` не указан и FBS/rFBS-склад ровно один, бот выбирает его автоматически; при нескольких складах запись остатков блокируется до явного выбора ID.

FBO используется только как признак наличия товара на складе OZON для независимого обнуления/восстановления Ozon FBS.


## 9. Восстановление после проблем со связью

Бот хранит в SQLite время последнего успешного опроса Marketplace API. Если между успешными опросами образуется разрыв больше примерно двух минут, после восстановления связи запускается расширенная сверка.

Для FBS-заказов бот дополнительно запрашивает историю `GET /api/v3/orders` за период сбоя (API позволяет запрашивать период до 30 дней) и проверяет статусы через `POST /api/v3/orders/status`. Если пропущенный заказ всё ещё новый, он снова появляется в Telegram с обычными кнопками выбора/создания поставки. Если заказ уже был обработан или отменён, бот присылает информационную сводку и сохраняет его в своей истории.

Уведомления об изменениях остатков используют persistent outbox: событие сначала сохраняется в SQLite и удаляется только после успешной отправки в Telegram. Поэтому временная недоступность Telegram не приводит к потере уже обнаруженного события. Перед повторной отправкой бот проверяет, что действие всё ещё актуально.

После разрыва также сравниваются сохранённые и текущие снимки FBS/WB. Прямые изменения между двумя снимками восстанавливаются. При этом текущие endpoint'ы остатков WB не дают точной внутридневной истории каждого перехода, поэтому ситуацию, когда товар успел появиться и снова закончиться целиком во время отсутствия связи, точно восстановить нельзя; бот явно предупреждает об этом после recovery.

## Что логично добавить следующим этапом

Следующий слой можно добавить без смены архитектуры: пороговые уведомления (`остаток < N`), журнал операций изменения FBS и отдельную команду ручного изменения остатка из Telegram.


Решения «Не добавлять», «Не обнулять FBS» и «Не возвращать» по товарам сохраняются в SQLite вместе с текущими FBS/WB-остатками. Повторный `/status` не показывает то же предложение, пока состояние товара не изменится. Любое фактическое изменение FBS или WB начинает новый цикл и сбрасывает прошлое решение для этого товара.
